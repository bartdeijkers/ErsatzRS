# HDR output characterization (ADR 0064)

This note records how the `OutputDynamicRange` filter shapes in
`ersatzrs-ffmpeg::filter::hdr` were derived. They were measured against the
shipped FFmpeg 9 runtime, not taken from documentation, because ADR 0064
requires decoded-output evidence rather than command generation alone.

Reproduce with the FFmpeg 9 runtime ErsatzRS ships
(`$HOME/.local/ffmpeg-9.0/bin/ffmpeg` on the maintainer machine, or any
`ErsatzRS-ffmpeg` build). Every command below is self-contained: the fixtures
are generated by `lavfi`, so nothing needs to be downloaded and nothing is
committed to the repository.

## Runtime under test

```
ffmpeg version n9.0-20260805
--enable-libx265 --enable-libplacebo --enable-vulkan --enable-libzimg
--enable-ffnvcodec --enable-vaapi --enable-amf --enable-opencl
```

## Fixtures

```bash
# HDR10: BT.2020/PQ 10-bit HEVC carrying ST 2086 + CTA-861.3 metadata
ffmpeg -f lavfi -i "testsrc2=size=640x360:duration=2:rate=25" \
  -vf "format=yuv420p10le,setparams=color_primaries=bt2020:color_trc=smpte2084:colorspace=bt2020nc:range=tv" \
  -c:v libx265 -profile:v main10 -pix_fmt yuv420p10le \
  -x265-params "master-display=G(13250,34500)B(7500,3000)R(34000,16000)WP(15635,16450)L(10000000,50):max-cll=1000,400:hdr-opt=1:repeat-headers=1" \
  -color_primaries bt2020 -color_trc smpte2084 -colorspace bt2020nc -color_range tv hdr10_src.mkv

# HLG: same picture, ARIB STD-B67 transfer
ffmpeg -f lavfi -i "testsrc2=size=640x360:duration=2:rate=25" \
  -vf "format=yuv420p10le,setparams=color_primaries=bt2020:color_trc=arib-std-b67:colorspace=bt2020nc:range=tv" \
  -c:v libx265 -profile:v main10 -pix_fmt yuv420p10le \
  -color_primaries bt2020 -color_trc arib-std-b67 -colorspace bt2020nc -color_range tv hlg_src.mkv

# SDR: tagged BT.709
ffmpeg -f lavfi -i "testsrc2=size=640x360:duration=2:rate=25" \
  -vf "format=yuv420p,setparams=range=tv:colorspace=bt709:color_trc=bt709:color_primaries=bt709" \
  -c:v libx264 -pix_fmt yuv420p sdr_tagged.mp4
```

## Finding 1: encoders propagate HDR10 static metadata automatically

Scaling `hdr10_src.mkv` with **no** metadata options, through either encoder,
preserves both metadata blocks and the BT.2020/PQ tags:

| Encoder | Mastering display | Content light | Stream tags |
|---|---|---|---|
| `libx265 -profile:v main10` | preserved | preserved (1000/400) | `bt2020nc / smpte2084 / bt2020` |
| `hevc_nvenc -profile:v main10` | preserved | preserved (1000/400) | `bt2020nc / smpte2084 / bt2020` |

This is why `preserve_hdr10_filter()` only pins the output tags for a PQ source
and deliberately emits **no** `-mastering_display` / `-content_light`: injecting
profile defaults there would overwrite the source's own, more accurate values.

## Finding 2: `setparams` is required; encoder `-color_*` options are not sufficient

Encoding an SDR source to HDR10 with `-color_primaries bt2020 -color_trc
smpte2084 -colorspace bt2020nc` as *output* options produced:

```
color_space=bt2020nc  color_transfer=unknown  color_primaries=unknown
```

The transfer and primaries did not survive, because the filtered frames still
carried the source tags. Appending
`setparams=range=tv:colorspace=bt2020nc:color_trc=smpte2084:color_primaries=bt2020`
produced correct signalling in every case. The SDR tonemap path in
`filter::tonemap` already used the same `setparams` tail, so the HDR10 path
follows the established shape.

## Finding 3: `-mastering_display` / `-content_light` work as input options

FFmpeg 9 exposes `-mastering_display[:<stream_spec>]` and
`-content_light[:<stream_spec>]`. Placing them before `-i` injects the metadata
into the encode, which is where ADR 0064 requires them (a per-stream input-side
description of the decoded source, not a generic output option).

```bash
ffmpeg -mastering_display "G(8500,39850)B(6550,2300)R(35400,14600)WP(15635,16450)L(10000000,1)" \
       -content_light "1000,400" -i sdr_tagged.mp4 ...
```

Verified present in the output as `Mastering display metadata` and
`Content light level metadata` frame side data.

## Finding 4: the SDR reference-white policy is 203 cd/m² and is exact

ITU-R BT.2408 defines HDR reference (diffuse) white as 203 cd/m². Feeding a
100% white BT.709 source through the generated `sdr_to_hdr10_filter()` chain:

```bash
ffmpeg -f lavfi -i "color=c=white:size=64x64:duration=0.2:rate=5" \
  -vf "format=yuv420p,setparams=range=tv:colorspace=bt709:color_trc=bt709:color_primaries=bt709" \
  -c:v libx264 -pix_fmt yuv420p white_sdr.mp4

ffmpeg -i white_sdr.mp4 -vf "zscale=t=linear:npl=203,zscale=p=bt2020,\
zscale=t=smpte2084:m=bt2020nc:r=tv:npl=203,format=yuv420p10le" \
  -frames:v 1 -f rawvideo white_pq.raw
```

The decoded 10-bit luma is **573** for every pixel. The PQ inverse-EOTF code
value for 203 cd/m² in 10-bit limited range is
`64 + 0.5806 × (940 − 64) ≈ 573`, so the mapping lands exactly on the standard
without inventing highlight detail above diffuse white.

`SDR_REFERENCE_WHITE_NITS` and the unit test
`sdr_to_hdr10_uses_the_documented_reference_white` pin this policy.

## Finding 5: signalling is stable across programme transitions

The three generated pipeline commands (PQ preserve, HLG→PQ, SDR→HDR10) were run
to real MPEG-TS and concatenated into one linear stream, imitating an HDR10
channel whose schedule mixes source dynamic ranges:

```bash
cat ts_sdr_to_hdr10.ts ts_pq_preserve.ts ts_hlg_to_pq.ts > mixed_channel.ts
ffprobe -select_streams v:0 -show_entries frame=color_primaries,color_transfer,color_space,color_range \
  -of csv=p=0 mixed_channel.ts | sort | uniq -c
```

Result — a single signalling class across all 75 frames, with no change at
either item boundary:

```
     75 tv,bt2020nc,bt2020,smpte2084,
```

Each individual output also carried both metadata blocks. This is the ADR 0064
"one stable output contract per stream" requirement proven from decoded frames.

## Finding 6: NVENC produces HDR10 for all three source types

Measured on an RTX 3080 Ti with `hevc_nvenc -profile:v main10`. All three cases
produced `hevc / yuv420p10le / bt2020nc / smpte2084 / bt2020` with mastering
display and MaxCLL/MaxFALL present:

| Source | Graph | GPU residency |
|---|---|---|
| PQ | `hwupload,setparams=…,scale_cuda=format=p010le` | stays on the GPU |
| HLG | software convert, then `format=p010le,hwupload_cuda,scale_cuda` | round trip |
| SDR | `hwdownload,format=<surface>,setparams(bt709),` convert, `hwupload_cuda` | round trip |

`setparams` works on CUDA surfaces, which is what lets the PQ case avoid a
download entirely.

Concatenating the three NVENC outputs into one stream again reports a single
signalling class across all 75 frames.

### Two hardware constraints the graphs must respect

- **`hwdownload` can only produce the surface's own software format.** An
  8-bit source in a CUDA surface must download as `nv12`; asking for `p010le`
  fails with `Invalid output format p010le for hwframe download`. A 10-bit
  source is the reverse. The format is therefore derived from the *source*
  pixel format, never from the profile's desired output depth.
- **`zscale` cannot convert from an unknown colourspace.** An untagged source
  fails with `code 3074: no path between colorspaces`. Untagged files are
  common, so the SDR-to-HDR10 chain always asserts its input tags first,
  falling back to BT.709 for anything the source did not carry.

## Finding 7: HDR10 survives overlays, subtitles, and HLS

The acceptance for `p8a-01` requires more than a bare transcode, so the full
shape was run against `hdr10_src.mkv`:

| Output | Graph | Result |
|---|---|---|
| HLS (fMP4) | `setparams`, `scale`, alpha `overlay` | `bt2020nc / smpte2084 / bt2020` + both metadata blocks |
| MPEG-TS | `setparams`, `scale`, alpha `overlay`, burned `subtitles` | same |

The alpha overlay was confirmed to actually composite rather than being silently
dropped: a pixel inside the overlay region reads `(61, 5, 0)` without it and
`(252, 0, 0)` with it.

## What is not yet characterized

- QSV, VAAPI, AMF, `VideoToolbox`, RKMPP, and V4L2M2M HDR10 output. No Intel,
  AMD, Apple, or Rockchip hardware was available. Those backends are *demoted
  to software encoding* for HDR10 profiles rather than allowed to emit SDR, and
  the `Output Dynamic Range` health check warns when that happens. See
  `docs/progress/parity/ffmpeg-9-performance-and-support.toml`.
- Dolby Vision inputs (milestone `p8a-02`).
