# ADR 0123: Support Level 2.5 teletext and external-editor workflows

## Status

Accepted (2026-10-11): the maintainer explicitly extended Phase 9 to authored
EN 300 706 Level 2.5 and QTeletextMaker interchange. The subsequent amendment
requires a demonstrably suitable client; Kodi is a candidate, not a dependency.
This supersedes ADR 0121's Level 1/1.5-only authored target. All other source,
playback, output, profile/Lua and engine-first obligations remain in force.
Maintainer amendment (2026-10-19): first accept an independently usable Level
1/1.5 delivery, then complete Level 2.5 while protecting that base. This changes
delivery and acceptance order, not the full Phase 9A scope or Phase 9B entry gate.

### Standalone Level 1/1.5 acceptance before Level 2.5

P9A-04 records two explicit acceptance boundaries in its existing F/V/X overview:
standalone Level 1/1.5 first, full authored Level 2.5 and complete Phase 9A next.

coverage. A capability missing only for Level 2.5 does not block the first
boundary; a shared repertoire, capacity, lifecycle or platform gap still does.

Use EN 300 706 clauses 9.4.1, 12.2, 12.3 and 15 to distinguish primary/national
characters, spacing attributes and Level 1.5 character replacement, including
G2, diacritics and the Level 1.5 G3 mode, from enhanced-only attributes/resources.

updates. Keep the standard's level-specific and decoder-dependent distinctions;
do not substitute an enhanced glyph oracle for an intended base representation.

semantic composition, rasterization, physical realization and full-origin

Keep all applicable profiles/themes/isolation, templates/zones, Lua timing/error/
restart, localized headed administration, source-caption/alternate-audio, playback

and installation workflow, never package-file mutation or script autoactivation.
Reuse existing application commands, configuration, addon trust and Lua controls.
Edit-policy validation includes indirect effects: a shared palette, object or
DRCS change can modify protected/generated cells even when its definition lies
outside their geometric bounds. Checking edited coordinates alone is insufficient.

### Phase 9A/9B ownership boundary

Phase 9A owns generic, addon-independent zone boundaries, edit permissions and
versioned metadata. During export/import the engine preserves and validates
addon-declared zones, template/theme references and dynamic-field bindings.
The addon owns the concrete zones and their meaning, layouts, colour themes,
templates and content; their production TV-guide realization belongs to Phase 9B.
Prove the generic mechanisms in Phase 9A with synthetic fixtures.

P9A-04 F2 requires neither a general visual template/theme editor nor production
TV-guide design. The complete agreed generic QTeletextMaker workflow, metadata
interchange, Free/Zone/Generated edit boundaries, package immutability and
explicit addon-version workflow remain mandatory. This clarifies ownership and
phase boundaries without lowering acceptance criteria or moving necessary
generic engine work to Phase 9B. Engine-first delivery remains mandatory:
production TV-guide work starts only after independent full engine acceptance.

### Durable design ownership

Existing graphics upserts have no draft revisions or export compare-and-swap;
addon-list lifecycle records have different ownership. Reuse their immutable
snapshot and transactional revision patterns, not their tables or `ConfigElement`.
Add a `TeletextDesign` head/tombstone, immutable `TeletextDesignRevision` records
and server-owned `TeletextDesignExportReceipt` records. Revisions retain a bounded,
versioned document, digest and original selection/edit-policy context. Receipts
retain the exact export revision, stable file mapping and resource baselines.
Keep these records when a profile or package is removed; do not cascade designs
from `AddonInstallation`.

Saving/importing requires the expected head revision and one immediate write
transaction; overflow, stale input or any failure preserves the previous head.
Validate the complete import before writing. The supplied sidecar cannot broaden
the receipt's edit permissions. Export only permitted design metadata, never a
general settings bag containing secret or local-file references. Package/profile
changes make the original selection context stale and require explicit resolution.

Explicit publication references an immutable `(design_id, revision, digest)` and
a fresh complete channel-selection fence. Saving/importing never sets an active
flag. Add durable pending/publication state with the actual service promotion
owner, not as a substitute for it. After restart, drafts and receipts remain
readable without automatic transmission; publication/restart must separately
restore only accepted generations under the existing profile/Lua timing contract.

The first implementation slice captures complete native originals into version-1
private design documents and restores historical previews through the same cold
compiler, without invoking installed packages. The initial explicit `original_only`
policy grants zero editing permissions; it is not a permanent authoring limitation
or external-editor acceptance. Opaque immutable export-receipt storage and
separate static publication are now implemented; native authoritative file/resource
receipt contents are implemented as an
internal export seam. Exact original ownership, sanitized producer metadata and
M29-derived editor context are retained. Editable concepts, indirect protected-cell
comparison and full editor integration remain required. Protected binary resources
are not claimed as QTeletextMaker-loadable dependency files. Existing OriginalOnly
documents and their bytes remain unchanged. Native confirmation
precedes CAS. Its deadline is a CPU/admission cutoff; admitted SQLite transactions
use the existing database timeout contract and do not pretend to undo committed
saves. See the interchange reference for the implementation boundary and P9A-01
for verified evidence; no milestone acceptance is changed.

The pending-request foundation now retains immutable `TeletextPublicationRequest`
rows and a per-channel current-request pointer. Requesting requires fresh complete
native compilation associated with the exact stored identity/revision/digest and
original selection. One immediate transaction then verifies the live nondeleted
design head, bounded immutable revision integrity, complete canonical channel
selection and independent current-request CAS before writing both records.
The expected live head is separate from the selected target revision: deliberate
publication of an older revision is allowed when the head is still current.
Requests remain readable after channel/profile/package removal and application
reconstruction. Pending intents never activate output. A separate immutable
accepted-generation history and per-channel pointer now select exact fully
recompiled frozen originals, with independent generation CAS and a versioned
complete wire/service fingerprint. Promotion rechecks the pending request, design
head/revision, original selection and accepted pointer in one immediate transaction.
Native recovery recompiles immutable originals and checks their fingerprint and
current selection without consuming pending intents or invoking packages. Saving
a newer draft or pending request does not replace accepted output.

Frozen qualification requires canonical captured requests with no guide channels
and no guide-source receipt; even a programme-empty channel is source-dependent.
Missing historical inputs do not certify static content. Guide-bearing/unknown
originals remain previewable and pending, but cannot gain active authority until
current-role/freshness proof exists. This is an unfinished promotion path, not an
accepted authoring limitation. Ordinary routes, active-publication Health, warm
publisher/recovery ownership and complete restart/Lua timing remain open. Durable
selection alone never proves per-output delivery or receiver cache reconciliation.

### Evidence and delivery order

The standalone Level 1/1.5 boundary above is the first delivery priority.
Its acceptance never satisfies or bypasses the following complete-engine gate.

P9A-01 is reopened for the expanded standards/interchange contract. P9A-04 accepts
the complete independent engine with synthetic pages before P9B-01 starts the
sole production TV-guide addon in ErsatzRS-Addons, inspired only by NOS guide
pages 200–299. Existing platform, subtitle, audio, lifecycle and output gates stay.

Require TSDuck transport checks, independent decoding of representative enhanced
functions and actual display/page/subpage navigation in a demonstrably suitable
client. Record exact client/decoder versions, settings, functions and limitations.
Kodi or an equivalent suitable client is allowed. TSDuck alone does not establish
Level 2.5 rendering; an editor preview is not a broadcast-client substitute.

Pin and verify the actual QTeletextMaker artifact for export → visibly open/edit/
save → import → preview → explicit publication evidence. Localize all changed
admin in every supported culture and retain headed browser, both-theme and
hydrated/no-JS proof. Provide a structured file/validation/preview workflow for
AI agents using the same application validation and publication boundary.

## Consequences

Existing transport and channel-isolation evidence remains valid for unchanged
behavior. Enhanced resource carriage, base fallback, draft persistence, editor
interchange and client display need additional implementation and acceptance.
Full Level 2.5 cannot be claimed with missing required parts. Any necessary engine
restriction must be explicitly proposed to the maintainer, not hidden in a
support label or accepted by substituting decoder availability.

## Alternatives Considered

- Retain a Level 1/1.5 authored target: rejected by the authorized scope extension.
- Treat QTeletextMaker as a lossless TTI validator: contradicted by its source.
- Store host metadata as custom TTI records: discarded by the editor's writer.
- Require Kodi at runtime or for acceptance: replaced by the maintainer's suitable
  client amendment.
