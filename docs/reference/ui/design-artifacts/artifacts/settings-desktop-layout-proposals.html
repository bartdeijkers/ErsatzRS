Admin UX layout study

Three desktop compositions from one component kit

Settings pages currently underuse wide screens, while Logs needs a denser operational layout. These proposals compare page composition without inventing three separate design systems.

Standardization boundary: standardize reusable components and their states; let each page compose them according to its content. Settings forms do not need to look like Logs, but both should use the same header, toolbar, controls, data surface, pagination, focus, and status contracts.

Responsive and states

  • Cards and fields stack when content pressure requires it; route links scroll on one axis.
  • Only a bounded table may scroll horizontally; the page reflows at 320 CSS pixels.
  • Loading, ready, empty, error, validation, saving, saved, and disabled states preserve a stable page shell.
  • Long translations wrap without clipping actions or control labels.

Accessibility

  • Use native headings, forms, labels, tables, links, and buttons; sortable headings expose aria-sort.
  • Keyboard order matches visual order, with visible focus and named pagination controls.
  • Verify at 200% zoom, 320-pixel reflow, reduced motion, and both themes.
  • Loading and success use status semantics; load and save failures use alert semantics.

Rust/Leptos map

  • SSR renders complete forms and raw POST fallbacks.
  • Keep Logs search, sort, page size, and paging in its existing narrow island.
  • Shared Rust components own markup and states; CSS modules own component styling.
  • Page modules own composition only: grouping, ordering, and width allocation.

Verification

  • Focused SSR tests for field grouping and raw form actions.
  • Keyboard and accessible-name tests for sorting and pagination.
  • Hydration lint plus Chromium and Firefox at wide and narrow viewports.
  • Validate route-tab discovery, selected state, long translations, and overflow with additional future settings pages.
