# Plan: give both list contracts the same strictness

## Context

The same add-on implements both list capabilities, but the two records fail in
opposite ways.

`AddonMediaListRecord` (`crates/ersatzrs-core/src/addon_media_list.rs:13`) is
strict:

```rust
#[serde(tag = "record_type", rename_all = "snake_case", deny_unknown_fields)]
```

`PlaylistEntry` (`crates/ersatzrs-scanner/src/remote_stream_playlist.rs:139`) is
permissive — no `deny_unknown_fields`, and `deserialize_string_vec` accepts
`null` where the media-list record would reject it.

So a misspelled field name in a `media-list.list` record rejects the whole
enumeration with a clear error, while the identical mistake in a
`remote-stream.list` record is silently discarded and the operator sees a stream
with missing metadata and no explanation. `docs/reference/addon-media-lists.md`
states "Unknown fields are rejected";
`docs/reference/remote-stream-playlist-manifests.md` makes that claim only about
the YAML manifest, not about enumeration output — so today's behavior is not
even documented as intentional.

`beeldengeluid.sh` and `youtube-list.ps1` build these records by hand-formatted
`printf` and hashtable literals. Hand-built JSON with silently ignored typos is
exactly the combination that produces a metadata bug nobody can locate.

Outcome: one documented strictness rule for both contracts, with the failure
mode chosen deliberately rather than inherited from whoever wrote each struct.

---

## Step 1 — Choose the rule

Strict is the right default and matches everything else on this boundary: the
manifest, the catalog, and the playlist manifest all use `deny_unknown_fields`.
An add-on's output is machine-generated by its author against a published
contract; tolerating unknown fields buys forward-compatibility that the
capability version already provides.

The counter-argument is real and must be answered before landing: strict output
parsing means the host cannot add an optional field to `remote-stream.list.v2`
without breaking add-ons that already emit it speculatively. The capability
version is the intended escape hatch — new fields go in `.v3`, and `.v2` stays
frozen. Write that down in the reference doc as the compatibility policy,
because it is currently implicit.

## Step 2 — Apply it

- Add `deny_unknown_fields` to `PlaylistEntry`.
- Align null handling. Either both records accept `null` for optional arrays or
  neither does; `deserialize_string_vec` exists only in the scanner. Given that
  provider tooling emits `null` readily — yt-dlp's `%(field)j` produces it for
  any missing value — accepting `null` as "absent" in both records is the
  defensible choice. Make it explicit and shared rather than a helper in one
  crate.
- Do this after
  [`addon-contract-crate-owns-ndjson.md`](addon-contract-crate-owns-ndjson.md)
  lands, so it is one change in one place instead of two that can drift again.

## Step 3 — Fix what the strictness exposes

Landing this will reject output that currently passes. Enumerate the official
packages' emitted keys against the record definitions before flipping the flag,
on both the POSIX and Windows implementations, and fix any mismatch in
`bartdeijkers/ErsatzRS-addons` first. Otherwise the first symptom is every
Beeld & Geluid list failing on upgrade.

## Step 4 — Regressions

- An unknown field rejects the enumeration in both contracts, with the offending
  field named in a bounded, provider-neutral message.
- `null` for an optional array and an omitted array behave identically in both.
- Rejection is atomic: no partial list is persisted and no generated playlist or
  managed file is written. The media-list path already promises this
  ("rejects the complete enumeration before persistence") — assert it for the
  Remote Stream path too.
- A rejected refresh preserves the previous complete definitions and playlist,
  as `docs/reference/remote-stream-playlist-manifests.md` already specifies.

against fixtures before flipping the flag.

Closeout gate:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo clippy --workspace --all-targets --features mysql -- -D warnings
./run.sh test-closeout
cargo xtask progress check
```

Document the rule and the version-bump compatibility policy in
`docs/reference/addon-media-lists.md` and
`docs/reference/remote-stream-playlist-manifests.md`; record the outcome in
`docs/progress/parity/addon-host-boundary.toml`.

## Out of scope

- Introducing a `.v3` capability. This plan sets the policy for how a future
  field would be added; it does not add one.
- The unrecognized-`availability` coercion, which is
  [`addon-availability-vocabulary-ownership.md`](addon-availability-vocabulary-ownership.md).
